# WP-1.2-02: syrp-ipc: InterprocessConnection and server, child-process coordinator and worker, service discovery

## Purpose
Wave 1.2 item 2: the `juce_events` inter-process classes from master plan §5.2 (L2 Events and state) and §4.12. It builds on `syrp-net` sockets and `NamedPipe` (WP-1.1-10), `syrp-process` `ChildProcess` (WP-1.1-08) and the owned `EventLoop` (WP-1.1-14), which a worker process runs. Master plan §5.3 lists the `interprocess` crate here, but `NamedPipe` is already in `syrp-net`, so this crate adds no third-party dependency. This WP creates `syrp-ipc`. Delivery: 3 PRs, each at most 1,200 changed lines (B1–B4, then B5–B6, then B7–B8).

## Behaviour
- B1. `InterprocessConnection::new(handler, Delivery, magic: u32)` where `handler` implements `ConnectionHandler` (`connection_made`, `connection_lost`, `message_received(MemoryBlock)`) and `Delivery` is `MessageThread(TaskSender)` (callbacks are posted to the message thread and get a `&MessageThread`) or `ConnectionThread` (callbacks run on the connection's reader thread, as the `callbacksOnMessageThread = false` option documents). `connect_to_socket(host, port, timeout)`, `connect_to_pipe(name, timeout)`, `create_pipe(name, timeout, must_not_exist)`, `disconnect`, `is_connected`, `connected_host_name` and `send_message(&[u8]) -> Result<(), IpcError>` (any thread; a message is written whole or the call fails).
- B2. Framing: each message is a header holding the magic number and the payload length, then the payload, as the class documentation describes. The byte order and header layout are Syrp's choice: write them into the rustdoc, pin them with a `b2_..._syrp_choice` test and list them under "Open questions" in the crate `AGENTS.md`, so the differential harness (WP-0.1-11) can later check interop with JUCE processes. A wrong magic number, or a length over the connection's configurable maximum (documented default), closes the connection with a coded error instead of allocating.
- B3. Callback order: `connection_made` comes before any `message_received`, messages arrive in send order, and `connection_lost` comes exactly once, after the last message. After `disconnect` or drop returns, no callback runs; drop joins the reader thread, and a `disconnect` from inside a callback does not deadlock.
- B4. `InterprocessConnectionServer`: `begin_waiting_for_socket(port, bind_address) -> Result<u16, IpcError>` (port 0 picks a free port and the bound one is returned), a factory closure called per accepted socket that returns the `InterprocessConnection` to own it (or `None` to refuse), and `stop`. Tests run client and server in one process over loopback, and over a pipe.
- B5. `ChildProcessCoordinator` and `ChildProcessWorker`, as their documentation describes: the coordinator launches the worker executable with a command-line token (`launch_worker_process(exe, unique_id, timeout, stream_flags)`), connects over a named pipe, pings at a regular interval and reports `handle_connection_lost` when the worker exits or stops answering within the timeout; `send_message_to_worker`, `handle_message_from_worker` and `kill_worker_process`. The worker side has `initialise_from_command_line(command_line, unique_id, timeout) -> bool`, `send_message_to_coordinator`, `handle_message_from_coordinator`, `handle_connection_made` and `handle_connection_lost`. The token format, the ping message and the default interval and timeout are written into the rustdoc (from the documentation where it gives them, otherwise pinned as Syrp choices). Tests spawn the test binary itself in a worker mode, which runs an `EventLoop`; they cover messages both ways, a killed worker, and a worker that stops pinging.
- B6. `ChildProcessManager`: launches `ChildProcess`es and calls a callback on the message thread when each exits (from a poll timer or an OS wait on a helper thread; document which), and never leaves a zombie process on Unix. Tested with short-lived helper processes.
- B7. `NetworkServiceDiscovery`: `Advertiser::new(service_type_uid, description, broadcast_port, connection_port, min_interval)` repeatedly sends a datagram announcing the service, and `AvailableServiceList::new(service_type_uid, broadcast_port)` collects `Service { instance_id, description, address, port, last_seen }` entries, notifies on change through a callback on the message thread and drops entries that have not been heard for a documented timeout. The datagram layout is Syrp's own, documented and pinned like B2. CI networks may block broadcast, so both types also take an explicit target address and tests use loopback unicast; a broadcast test is best effort and skips with a message.
- B8. Errors use the new `errors/ipc.toml` domain (`SYRP-IPC-0001`...); `IpcError` implements `Diagnostic` and keeps the `syrp-net` or `syrp-process` error as its source.

## Platforms
Linux, macOS and Windows are required, and PR CI must pass B1–B8 on all three. All platform differences live in `syrp-net` and `syrp-process`; this crate has no `unsafe` and no platform code.

## Not in this WP
Encryption or authentication of connections, JUCE wire-compatibility beyond documenting the framing (the harness checks it later), and the `inspect` IPC port (A11).

## Crate setup
Create `crates/core/ipc/` with `Cargo.toml` (inherit `version`, `edition`, `rust-version`, `repository`, `authors`, `publish` from the workspace; `[lints] workspace = true`), `[package.metadata.syrp] layer = "L2"`, an `AGENTS.md` following `docs/agents/crate-agents-template.md`, and `src/lib.rs`. Workspace members are globbed, so no root edit is needed.

## Rules that apply to every WP
- Clean room: work only from this spec, the master plan (`docs/design/master-plan.md`) and public JUCE *documentation* for behaviour. Never fetch or recall JUCE source code.
- Name every test after the behaviour it proves, prefixed with its id, for example `b3_try_push_fails_when_full`.
- Run `cargo syrp wp show WP-1.2-02` first and `cargo syrp wp check WP-1.2-02` last. A PR is ready only when that command exits 0.
- Shared files (workspace `Cargo.toml`, CI, `deny.toml`) are not yours. If you need a new third-party dependency in `[workspace.dependencies]`, declare it with an explicit version in your crate's own `Cargo.toml` and list it in the PR front matter `deps_added`; the adversarial verifier reviews it.
