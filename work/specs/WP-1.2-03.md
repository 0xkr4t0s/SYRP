# WP-1.2-03: syrp-state: node store, reference counts, change log and listener delivery

## Purpose
The native state store from master plan §5.9 and ADR 0003 D2, built on the design the WP-0.2-15 spike validated (`docs/design/0005-state-arena-spike.md`, "Recommendation"). Read that record first: this spec turns its recommendation into requirements, and its scenario table is your starting test list. `syrp-compat-state` (WP-1.9-01) puts JUCE's `ValueTree` API over this crate, so nothing here is JUCE-shaped beyond the semantics. The spike crate `crates/spikes/state-arena/` may be read and its ideas reused; do not depend on it. Delivery: 3 PRs (B1–B3, then B4–B6, then B7–B8).

The store takes `&MessageThread` from `syrp-loop-api` directly; `syrp-events` and `syrp-io` (master plan §5.3) are not needed until persistence, which is a later WP.

## Behaviour
- B1. `Store`: one per document, `!Send`, every mutation takes `&MessageThread`. Nodes live in a slotmap arena; each has a type `Identifier`, properties as a `Vec<(Identifier, Var)>` sorted by identifier, and an ordered `Vec` of children. `NodeRef` is a handle (store plus key): clone is shallow, equality is identity. `NodeKey` is a `Copy` key that holds no count; `store.upgrade(key)` returns a `NodeRef` while the node is alive. Operations: `create`, `node_type`, `property`, `has_property`, `set_property`, `remove_property`, `remove_all_properties`, `properties` (iteration), `parent`, `child(i)`, `num_children`, `index_of`, `child_with_type`, `child_with_property`, `add_child(child, Option<usize>)` (`None` or an index past the end appends, as `ValueTree::addChild` documents for out-of-range indices), `remove_child`, `remove_all_children`, `move_child(from, to)`, `root` (the topmost ancestor), `is_ancestor_of`.
- B2. Errors, not booleans: adding a child that already has a parent, adding an ancestor under its own descendant, passing a node from another store, and using a dead key each return a coded `StateError` from the new `errors/state.toml` domain (`SYRP-STATE-0001`...). The store is unchanged after an error.
- B3. Reference counts, as in the spike: a node's count is its live handles, its subscriptions, one for its parent link and one per undelivered log record that names it. At zero the slot is freed and each child loses its parent link and one count. A detached subtree lives while referenced and is reclaimed after; `store.live_nodes()` reports arena occupancy for tests. A parent freed while a child is held leaves the child parentless (spike open question 6; pin it with a test named `b3_..._syrp_choice`).
- B4. Change log: every mutation appends records (`PropertyChanged { node, id, old, new }`, `PropertyRemoved`, `ChildAdded { parent, child, index }`, `ChildRemoved`, `ChildMoved { parent, from, to }`, `ParentChanged { node }`) with a monotonic sequence number. Records carry what is needed to reverse them (WP-1.2-04 builds undo on this). Setting a property to its current value or removing a missing property appends nothing (open questions 7 and 9, pinned as Syrp choices). Readers other than delivery register a `LogCursor`; records are kept until every registered cursor has passed them, and dropped after delivery when there are none.
- B5. Delivery and targets: listeners subscribe per node and get a `Subscription` guard that unsubscribes on drop and holds a count. `PropertyChanged`, `PropertyRemoved`, `ChildAdded`, `ChildRemoved` and `ChildMoved` go to listeners on the node and every ancestor, computed at delivery time; `ParentChanged` goes to the node's own listeners only. Delivery runs after the mutation's borrow is released; a listener's own mutations apply at once and are delivered after the current record's remaining listeners. Listener order is the spike's (node first, registration order, then each ancestor upwards) and is documented as not yet parity-checked. A panicking listener does not wedge the store: a drop guard clears the delivery flag, and the next mutation delivers the remaining records.
- B6. Cheap delivery, as the spike recommends: listener lists in a secondary map keyed by node, a reusable snapshot buffer, events passed by `NodeKey` with handles built only on request, and a per-store count of subscriptions so a store with no listeners skips delivery. With `syrp_rt::no_alloc` around it, `set_property` with an `i32` or `f64` value allocates nothing after warm-up, with and without two listeners.
- B7. `deep_copy(&self, node) -> NodeRef` (a detached copy of the subtree) and `is_equivalent(a, b)` (same type, same property set in any order, equivalent children in order). Proptest (ADR 0003 D7): random sequences of create, set, remove, add, remove-child, move, drop-handle and subscribe keep every invariant: parent and child links agree, no cycles, properties stay sorted, counts equal a census of handles, links, subscriptions and pending records, and dropping every handle and draining the log frees every slot.
- B8. Instruction-count benchmarks (`cargo bench -p syrp-state`, Callgrind, same harness style as `crates/foundation/simd/benches/instructions.rs`) for `property`, `set_property` without listeners and `set_property` with a listener on the node and its parent, at 4, 16 and 64 properties. Record the numbers in the crate `AGENTS.md`; CI does not gate on them yet.

## Not in this WP
Undo (WP-1.2-04), typed schemas (`#[derive(StateSchema)]`), XML, JSON and binary persistence, `PropertiesFile`, the synchroniser, and any JUCE-shaped type (WP-1.9-01). Do not test the spike's open questions as parity.

## Crate setup
Create `crates/core/state/` with `Cargo.toml` (inherit `version`, `edition`, `rust-version`, `repository`, `authors`, `publish` from the workspace; `[lints] workspace = true`), `[package.metadata.syrp] layer = "L2"`, an `AGENTS.md` following `docs/agents/crate-agents-template.md`, and `src/lib.rs`. Workspace members are globbed, so no root edit is needed.

## Rules that apply to every WP
- Clean room: work only from this spec, the master plan (`docs/design/master-plan.md`) and public JUCE *documentation* for behaviour. Never fetch or recall JUCE source code.
- Name every test after the behaviour it proves, prefixed with its id, for example `b3_try_push_fails_when_full`.
- Run `cargo syrp wp show WP-1.2-03` first and `cargo syrp wp check WP-1.2-03` last. A PR is ready only when that command exits 0.
- Shared files (workspace `Cargo.toml`, CI, `deny.toml`) are not yours. If you need a new third-party dependency in `[workspace.dependencies]`, declare it with an explicit version in your crate's own `Cargo.toml` and list it in the PR front matter `deps_added`; the adversarial verifier reviews it.
