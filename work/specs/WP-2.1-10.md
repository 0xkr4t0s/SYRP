# WP-2.1-10: syrp-dsp-core: processor model and chains, FFT, windowing, lookup tables and maths helpers

## Purpose
Wave 2.1 item 10: `syrp-dsp-core` from master plan §5.2 and §5.3 (`dsp-core -> audio-basics, simd [rustfft, realfft]`), the base of `juce_dsp`. It holds the processor model that every `syrp-dsp-*` crate implements, the FFT (master plan §4.9: wrap `rustfft` and `realfft` and match JUCE's scaling and ordering), windowing, lookup tables and the maths helpers. `AudioBlock` and `ProcessSpec` are already in `syrp-audio-api` (WP-0.2-02) and `SIMDRegister` is answered by `syrp-simd` lane packs (WP-0.2-14); both are frozen contracts, so this crate uses them and records gaps instead of changing them. Per-instance DSP is written against `syrp_simd::Sample` (ADR 0003 D5). This WP creates `syrp-dsp-core`. Delivery: 3 PRs, each at most 1,200 changed lines (B1–B2, then B3–B4, then B5–B7).

## Behaviour
- B1. Processor model: `DspSpec { sample_rate, max_block_size, channels }` built from `syrp_audio_api::ProcessConfig` plus a channel count (JUCE's `ProcessSpec`). `trait DspProcessor<S: Sample>: Send` with `prepare(&DspSpec)`, `reset()` and `process(&mut self, ctx: &mut ProcessContext<'_, S>)`, where `ProcessContext` is replacing (one `AudioBlockMut`) or non-replacing (an input `AudioBlock` and an output `AudioBlockMut`) and carries the `is_bypassed` flag, as `ProcessContextReplacing` and `ProcessContextNonReplacing` document. A processor must not allocate in `process` or `reset`.
- B2. Composition: `ProcessorChain` over tuples of up to 8 processors with `get::<N>()`, `set_bypassed::<N>(bool)` and `is_bypassed::<N>()`, as `ProcessorChain` documents (bypassed processors are skipped, not run with the flag set). `ProcessorDuplicator<P, State>` (JUCE's: one processor per channel sharing a state object) packs channels into lanes when `P` is `Sample`-generic and keeps one instance per channel otherwise, the same rule WP-1.9-02 B3 uses. `ProcessorWrapper` adapts a processor that has no `DspProcessor` impl. Tests: a chain of gains equals the product, bypass skips, and duplicated mono processors equal per-channel instances (`f32-arith`).
- B3. `Fft::new(order)` (size 2^order, `order` up to a documented limit; larger is a coded error): `perform(&[Complex], &mut [Complex], inverse)`, `perform_real_only_forward_transform(&mut [f32], only_non_negative_frequencies)`, `perform_real_only_inverse_transform(&mut [f32])` and `perform_frequency_only_forward_transform(&mut [f32], ignore_negative_frequencies)`, with the buffer sizes, interleaved complex layout, bin ordering and scaling the `dsp::FFT` documentation gives. Built on `rustfft` 6.4 and `realfft` 3.5 (MIT OR Apache-2.0) with plans and scratch made in `new`, so `perform*` never allocates. Where the documentation does not state the inverse scaling, choose, pin it with a `b3_..._syrp_choice` test and list it under "Open questions" in the crate `AGENTS.md`. Tests (`fft` profile): impulses, sines and random signals against a naive DFT, forward then inverse round trips, and every order from 0 to 14.
- B4. `WindowingFunction::new(size, kind, normalise, beta)` for `Rectangular`, `Triangular`, `Hann`, `Hamming`, `Blackman`, `BlackmanHarris`, `FlatTop` and `Kaiser`, with `fill_windowing_tables` and `multiply_with_windowing_table`, using the standard published window formulas and the `normalise` meaning the documentation gives. Tests compare each window with its closed form and check symmetry.
- B5. Tables: `LookupTable<S>` (`initialise(fn, size)`, `get_unchecked`, `get` with clamping, linear interpolation between entries) and `LookupTableTransform<S>` (a function over a range, `process_sample`, `process` over a slice, `calculate_max_relative_error`), as documented; lane-generic over `Sample`.
- B6. Maths helpers: `FastMathApproximations` (`sin`, `cos`, `tan`, `sinh`, `cosh`, `tanh`, `exp`, `log_nplusone`, each over the input range the documentation states, with the maximum error measured and written into the rustdoc), `Phase` (wrapping phase accumulator), `LogRampedValue` (as documented), `Matrix<T>` (construction, identity, Toeplitz and Hankel builders, add, multiply, transpose, `solve`, as `dsp::Matrix` documents), `Polynomial<T>` (evaluate, add, multiply, as documented) and `SpecialFunctions` (the Bessel I0 used by the Kaiser window, and the elliptic helpers `FilterDesign` needs in WP-2.1-11).
- B7. RT and SIMD: every `process`, `perform*`, table and helper call is allocation-free (`syrp_rt::no_alloc` tests). The crate `AGENTS.md` maps each `SIMDRegister` operation to its `syrp_simd` equivalent and lists missing ones under "Known gaps". `benches/fft.rs` counts instructions (Callgrind) for an order-10 real forward transform. Errors use the new `errors/dsp.toml` domain (`SYRP-DSP-0001`...).

## Not in this WP
Filters (WP-2.1-11), effects (WP-2.1-12), convolution and oversampling (WP-2.1-13), the `syrp-dsp` umbrella crate, and a parallel FFT.

## Rules that apply to every WP
- Clean room: work only from this spec, the master plan (`docs/design/master-plan.md`) and public JUCE *documentation* for behaviour. Never fetch or recall JUCE source code.
- Name every test after the behaviour it proves, prefixed with its id, for example `b3_try_push_fails_when_full`.
- Run `cargo syrp wp show WP-2.1-10` first and `cargo syrp wp check WP-2.1-10` last. A PR is ready only when that command exits 0.
- Shared files (workspace `Cargo.toml`, CI, `deny.toml`) are not yours. If you need a new third-party dependency in `[workspace.dependencies]`, declare it with an explicit version in your crate's own `Cargo.toml` and list it in the PR front matter `deps_added`; the adversarial verifier reviews it.
