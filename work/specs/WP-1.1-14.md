# WP-1.1-14: syrp-events: owned desktop MessageLoop implementations (epoll, CFRunLoop, Win32)

## Purpose
The owned loops from master plan §5.5 (kind 1) and Wave 1.1 item 14: the real message loop an app runs on its main thread, on Linux, macOS and Windows. Each implements the frozen `syrp_loop_api::MessageLoop` contract (WP-0.2-01) through the hooks that contract gives implementers (`TaskSender::new`, `CallbackGuard::new`, `unsafe MessageThread::new_unchecked`), so nothing under `contracts/` changes. Anything the trait cannot express goes in `syrp-events`' own API. If the contract proves insufficient, stop and ask for a contract-change WP instead of working around it. This WP creates `syrp-events`. Timers, `Coalescer` wrappers and broadcasters (Wave 1.2 item 1) come later in the same crate. Delivery: 3 PRs (B1–B4 with the Linux backend, then B5–B6, then B7–B9).

## Behaviour
- B1. `EventLoop::new() -> Result<EventLoop, EventsError>`, created on the thread that becomes its message thread. It is `!Send`, and there is at most one per thread (a second one is a coded error). It implements `MessageLoop` and adds `run()` (until quit), `run_for(Duration)`, `dispatch_pending()` (one non-blocking pass, for embedding in a foreign loop), `with_token(f)` and `quit_handle() -> QuitHandle` (`Send + Sync`, quits from any thread). Tokens are made with `MessageThread::new_unchecked` only inside the loop's own callbacks, each behind a `// SAFETY:` comment.
- B2. Contract conformance: the behaviour `crates/contracts/loop-api/AGENTS.md` lists under "Invariants" holds for `EventLoop` too. `post` never runs a task inline, and tasks from one thread run in post order. `post_and_wait` on the loop thread fails with `SYRP-LOOP-0001`, and a dropped loop wakes waiters with `SYRP-LOOP-0003`. Due timers fire in (due, creation) order, periods under 1 ms become 1 ms, and a timer made in a callback first fires one period later. Dropping a guard cancels at once, even from inside its own callback. No borrow or lock is held while a callback runs. Write these checks as one test suite generic over a small driver trait, and run it against `ManualLoop` and against `EventLoop` on every platform, so the two cannot drift.
- B3. Real time: timers use the monotonic clock and absolute deadlines. A timer that falls behind (the thread was blocked) fires once and then keeps its phase; it does not fire a burst to catch up. This differs from `ManualLoop::advance` on purpose: document it, and pin it with a `b3_..._syrp_choice` test. CI timing assertions use loose bounds (a 10 ms timer over 300 ms fires 20–31 times).
- B4. Linux backend: `epoll` with an `eventfd` to wake for posted tasks and either `timerfd` or the `epoll_wait` timeout for timers. `add_fd(fd, Interest, callback) -> FdGuard` lets later peers (X11, Wayland) and `syrp-ipc` add their file descriptors; the loop opens no display connection itself. Build it on `libc` directly, or on a small crate such as `rustix`, and list it in `deps_added`.
- B5. macOS backend: the current thread's `CFRunLoop`, with a `CFRunLoopSource` for posted tasks and `CFRunLoopTimer`s for timers (through `objc2-core-foundation` or `core-foundation`). `run()` runs the run loop. On the main thread, task and timer delivery also works when something else drives the run loop (for example `NSApplication run`, later in `syrp-app`), with no call to `run`. Tests that need the main thread live in a `harness = false` test binary.
- B6. Windows backend: a hidden message-only window (`HWND_MESSAGE`) with its own window class. Posted tasks wake it with `PostMessageW` of a private message, and timers come from the loop's own deadline heap through `MsgWaitForMultipleObjectsEx` with a timeout, not `SetTimer` (which has coarse resolution). Messages for other windows on the thread are translated and dispatched, so future peers work.
- B7. VBlank: until a peer crate registers a display source, `on_vblank(peer, f)` is driven by a fallback timer at 60 Hz, with refresh times on the loop's timer clock. `EventLoop::vblank_driver(peer) -> VBlankDriver` lets a peer (Wave 3) take over and call `driver.fire(at)` per refresh; while a driver exists, the fallback timer for that peer stops. Tested with a fake driver.
- B8. Migration: a page under `docs/migration/` maps `MessageManager` (`callAsync`, `callFunctionOnMessageThread`, `isThisTheMessageThread`), `CallbackMessage`, `Message` and `MessageListener` to `post`, `post_and_wait` and `TaskSender::is_message_thread`, and records `MessageManagerLock` as the deviation master plan §5.5 describes.
- B9. Errors are added to `errors/loop.toml` from `SYRP-LOOP-0004` (that domain already covers loop implementations): a second loop on one thread, an OS failure while creating the loop (with the OS error), and an unsupported target. `EventsError` implements `Diagnostic`. The frozen `LoopError` is unchanged.

## Platforms
Linux, macOS and Windows are required. PR CI must pass B1–B9 on ubuntu-24.04 x64, macos-15 arm64 and windows-2025 x64. iOS, Android and the web are out of scope: the crate compiles there, and `EventLoop::new` returns the "unsupported target" error. Every `unsafe` block has a `// SAFETY:` comment, and TSan runs nightly on this crate (§9.8).

## Not in this WP
Hosted loops for plugins (CLAP, VST3 `IRunLoop`, AU and AAX; Phase 5), `Timer`/`MultiTimer`/`AsyncUpdater` wrappers and `Broadcaster<T>` (Wave 1.2 item 1, a later WP in this crate that depends on this one), `MessageManagerLock` (not provided, master plan §5.5), app lifecycle (`JUCEApplicationBase`).

## Crate setup
Create `crates/core/events/` with `Cargo.toml` (inherit `version`, `edition`, `rust-version`, `repository`, `authors`, `publish` from the workspace; `[lints] workspace = true`), `[package.metadata.syrp] layer = "L2"`, an `AGENTS.md` following `docs/agents/crate-agents-template.md`, and `src/lib.rs`. Workspace members are globbed, so no root edit is needed.

## Rules that apply to every WP
- Clean room: work only from this spec, the master plan (`docs/design/master-plan.md`) and public JUCE *documentation* for behaviour. Never fetch or recall JUCE source code.
- Name every test after the behaviour it proves, prefixed with its id, for example `b3_try_push_fails_when_full`.
- Run `cargo syrp wp show WP-1.1-14` first and `cargo syrp wp check WP-1.1-14` last. A PR is ready only when that command exits 0.
- Shared files (workspace `Cargo.toml`, CI, `deny.toml`) are not yours. If you need a new third-party dependency in `[workspace.dependencies]`, declare it with an explicit version in your crate's own `Cargo.toml` and list it in the PR front matter `deps_added`; the adversarial verifier reviews it.
